## Current source behavior

A **managed alert** is eligible only while firing, marked for automatic investigation, owned by the product, and matched to exactly one approved rule. An explicit fingerprint identifies the alert; when absent, a stable fingerprint is derived from its labels. Unapproved or non-firing observations cannot start work. The current rule inventory has eight approved alerts, and the source monitor adds one alert-service outage rule. The [source contract](../../raw/v1/c4-operational-incidents.feature) calls this an operational incident, distinct from a product change.

An **incident epoch** is one firing run of a managed rule and fingerprint. Repeated observations while active retain its identity. After resolution, a return within the 30-minute cooldown retains the old epoch; a return after that cooldown starts a new one. A successful alert-list observation can resolve missing incidents. An unavailable alert list cannot prove resolution. Three consecutive unavailable polls start or retain a separate alert-service outage investigation. A successful poll resets that failure streak. See the [monitor](../../raw/v1/stack-alert-monitor.py) and its [checks](../../raw/v1/stack-alert-monitor-test.py).

One epoch has one stable **investigation request**. Its instruction includes the approved rule meaning and bounded, payload-free metric facts: no more than 12 finite samples per query, approved short labels, and a bounded serialized snapshot. Metric unavailability is explicit. Untrusted alert payloads and labels do not become instructions. The investigation is read-only: report observed facts, probable cause, impact, uncertainty, and recommended next action without claiming unavailable checks or performing remediation. A failed submission retries the same request identity and instruction. See the [monitor](../../raw/v1/stack-alert-monitor.py) and [task rules](tasking.md).

The current operator can inspect the alert page, monitor log, and task list. The source keeps an incident row separately from the task authority; it does not join a finding into an incident-specific owner read. A task's answer may be a finding, failure, or unavailable judgment. None authorizes a product edit. The [slice plan](../plan/11-operational-incidents/plan.md) adds a joined owner read and keeps investigation and change governance separate.

## v2 command and query authority

A poll is an external observation, not by itself an accepted domain fact. A command validates a managed observation against the approved rule set, then records incident epoch state and the stable investigation request before submitting work. That recorded intent is authoritative for retries. The task authority alone admits, executes, and settles the investigation task. If submission acknowledgement is lost, the same request identity is retried; the task admission rule prevents a second accepted task. The incident read joins the incident decision history with the task's current progress or outcome. Derived reads can be rebuilt without resubmitting investigations. [Slice decisions](../plan/11-operational-incidents/decisions.md) define these v2 refinements.

An authenticated owner can query active and historical epochs, eligibility/refusal, observation freshness, evidence availability, request identity, task status, and finding or failure. A foreign owner learns nothing from incident or task reads. A resolved alert may still have an unfinished or failed task. The owner decides whether to close or follow up; any governed product change remains a separate decision. See [task lifecycle](task-lifecycle.md) and [slice scenarios](../plan/11-operational-incidents/spec.feature).
