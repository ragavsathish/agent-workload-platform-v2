## Worker and result topology

The existing Grain knowledge aggregate and task stream are authoritative for source, task link, result digest, suggestions, review actions, daily versions, and owner scope. Build an Effect TypeScript worker around the three v1 processing modes. The v1 task runner launches a Gondolin guest with constrained loopback model, classifier, and writer destinations; its stdout result is only a status summary. V2 needs a validated, attributable result envelope delivered to the Grain knowledge service. Do not infer suggestions from the v1 status summary or trust a generic task completion as proof of a graph write. Use a transactional outbox or equivalent persisted handoff to close the crash gap between task completion and result incorporation. Keep each mode's retry key stable and expose conflict on digest mismatch.

V1 journal processing gates routine sentences, invokes an Ollama structured response at temperature zero, then checks exact normalized evidence and type cues. Classification calls SystemOne, requires a 0.60 confidence threshold by default, then invokes candidate extraction; `none` and low-confidence paths write no candidate graph data. Daily prose uses a separate prompt and validates local-date source membership. Retain these as evidence-backed starting behavior, then qualify actual quality rather than assuming heuristic or format validity implies accuracy. The processor currently computes capture ID from session and message without owner; V2 identity and authorization must include owner. Source spans and content need protected storage and redacted task progress.

## Graph and migration topology

Project Grain knowledge decisions into the pinned ORC ontology package at commit `033f0ab7c2be46fd8bddd5fc94e362d074afac34`. Its `create-ontology!`, `create-concept!`, `update-concept!`, and ontology-scoped `get-concept-by-uri` work with the Grain store. Each owner has a deterministic custom ontology ID. Concept URIs and command IDs derive from owner and item identities; source ID, result ID, and owner hash stay in ORC provenance. Grain review decisions remain authoritative. Reads cross-check Grain item status, so an ORC concept left by a rejection is hidden. Broad ORC BFS is not used because it is not ontology scoped. The model-backed `build-ontology-from-sources` is exposed only for explicit candidate exploration in a separate owner/source ontology; its direct graph output lacks AWP review gating and cannot publish accepted knowledge. ORC's built-in failure/success/problem taxonomy is not imposed on personal journals or assertions. V1 Oxigraph quads remain in private snapshot packages for audit and reconciliation.

The v1 `digital_twin.py` migration previews legacy page and prediction counts and can apply the typed projection update with a supplied time zone. It is not a full data migration, backup, owner mapping, or reconciliation. Build a separate snapshot exporter and importer. Manifest graph names, counts, canonical quad digests, source IDs, review order, daily page versions, and unmapped resources. Capture the actual old Oxigraph dataset through authorized access only; avoid checking private triples into this repository. Reconcile to Grain resources and projected query results. Keep a read switch and a source backup for rollback. The date-based v1 daily page ID may overwrite versions; report unrecoverable historical versions rather than inventing them.

## Qualification and dependencies

Deterministic acceptance tests use synthetic owner data. Live quality qualification needs the configured Ollama model, SystemOne classifier, reviewed corpus, and pinned prompt/model versions. The local model, classifier, and Oxigraph services were reachable during the build. A private Oxigraph export with 2,915 quads across four graphs was written outside the repository. V1 application environment and `schema:sender` metadata established an owner mapping for 253 source messages. A private normalized import preview reconciled 413 mapped resources; 12 metadata resources lacked a provable source link and remain quarantined. No reviewed quality corpus was available. A synthetic real-model smoke is useful for protocol testing but does not pass the quality gate. The external tailnet/public deployment gate from slice 06 is also still open and remains a separate prerequisite for deployed cutover.
